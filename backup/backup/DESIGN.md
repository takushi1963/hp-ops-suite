# バックアップ設計思想（Design Rationale）

この文書は「なぜこのバックアップ構成なのか」を説明します。  
OS再インストール時や、将来の見直し・引き継ぎ・AIレビューを想定しています。

---

## 設計ゴール（Design goals）

1. **復旧できる（Recoverability）**
   - OSが消えても復旧できること
2. **見える（Transparency）**
   - 状況を1コマンドで把握できること
3. **自動化（Automation）**
   - systemd timer で無人運用できること
4. **安全（Safety）**
   - 自動で破壊的操作を行わないこと
5. **資料化（Documentation-first）**
   - スクリプトが実行可能ドキュメントであること

---

## なぜ dd と rsync の二系統か（Why both dd and rsync）

### 1) フルディスク（dd）

**目的**
- SSD/ディスク故障など「完全損失」からの復旧

**強み**
- パーティション、ブートローダ、OSを丸ごと保持できる

**弱み**
- サイズが大きい
- 時間がかかる
- 頻繁実行には向かない

**設計方針**
- 頻度は低め
- 世代管理で「最後の正常」を守る
- 自動で上書きしない

---

### 2) 差分（rsync）

**目的**
- OS破損、設定ミス、誤操作からの復旧

**強み**
- 速い
- ファイル単位で戻せる
- 部分復旧が容易

**弱み**
- ブートローダ単独の復旧は不得意
- ファイルシステム依存

**設計方針**
- 定期実行で“普段使いの保険”
- dd を置き換えない（補完関係）

---

## なぜ Git をバックアップの一部とするか（Why Git matters）

この環境では、スクリプトと設定そのものが資産です。

Git は以下のために使います：
- バックアップ“仕組み”の復元
- 設計の変遷の追跡
- ChatGPT による迅速な理解とレビュー

Git に入れないもの：
- ディスクイメージ
- アーカイブ実体
- ランタイムログ

---

## ステータス優先（Status-first）

復旧や判断の前に必ず：
1. `backup-status.sh` を実行
2. マウント状態確認
3. 最新バックアップ確認
4. 復旧方針決定（dd / rsync）

---

## 想定障害と対応（Failure scenarios）

| 障害 | 対応 |
|---|---|
| SSD故障 | dd で復旧 |
| OSが起動しない | rsync で復旧 |
| スクリプト破損 | Git から復元 |
| 状態不明 | まず status |

---

## 非対象（Non-goals）

- クラウド同期
- リアルタイムミラー
- 自動復旧

理由：運用を **予測可能・監査可能・単純** に保つため。

## 最後に

このバックアップは、
- 人間が読める
- AIが理解できる
- 文書から再構築できる  
ことを最優先にしています。
